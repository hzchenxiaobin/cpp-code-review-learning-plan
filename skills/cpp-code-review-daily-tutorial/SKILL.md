# C++ 代码检视每日图文教程

把某一天的学习任务写成一篇能独立学习、能跟着操作、能检查成果的教程，而不是把学习计划改写成更长的提纲。

## 工作流程

### 1. 确定当日范围

- 优先使用用户提供的学习计划、仓库或当日主题；本仓库的默认计划是 README.md 中的 120 天日程（Day 1–120，按周分 5 个阶段）。
- 用户只给天数时，在计划中按 `Day N` 定位对应行及其所属周的主题，不要重复询问已存在的信息。
- 读取目标日，并快速查看前一天和后一天，避免重复讲解或提前引入过多新概念。
- 计划来自标准 Markdown 日程且仓库提供脚本时，可运行：

```bash
python3 scripts/tutorial_tools.py extract README.md --day 45
```

- 无法确定学习材料或目标日期时，只询问缺少的一项信息。

### 2. 设计最小学习闭环

用一条主线组织全文：

```text
真实缺陷 → 直觉解释 → 准确概念 → 图解机制 → 检视演练 → 验证结果 → 常见误判 → 练习验收
```

遵守以下约束：

- 只覆盖当天目标所需的前置知识，必要短板用“前置补给”简短解释。
- 选择一个贯穿全文的具体代码案例，例如一个约 50 行的 `TaskQueue`、`ConfigLoader` 或 `ResourceManager` 类，当天围绕它检视不同维度，避免每个概念换一套例子。
- 先解释“这类代码为什么容易出问题”，再解释“规则是什么”和“检视时怎么查”。
- 对可能变化的工具版本、命令和编译器行为先核实；不凭记忆编造告警内容或 sanitizer 行为。

### 3. 编写完整教程

仓库提供 [references/tutorial-template.md](../../references/tutorial-template.md) 时按其默认结构生成 Markdown；否则使用内置结构：导语 → 前置补给 → 概念讲解（配图）→ 检视演练 → 工具验证 → 常见错误与误判 → 练习 → 验收清单 → 总结。可根据当天内容合并小节，但不得删除实践、常见错误、练习、验收和总结。

写作要求：

- 使用自然、清楚的中文，短段落，多具体例子，少堆砌术语。
- 首次出现的专业术语（如 RAII、use-after-free、内存序、迭代器失效）用一句普通话解释，并保留必要英文原名。
- 类比之后必须补一句“对应到技术上是……”，指出类比不能覆盖的边界。
- 每介绍一个核心概念，立即配一个小例子或一张图。
- 缺陷示例提供所需文件、关键完整实现、编译运行命令（至少 `-Wall -Wextra`，工具链相关课程按需加 `-fsanitize=address,undefined` 等）和预期结果；不要只给无法运行的碎片。
- 能实际编译运行时执行代码并记录真实输出；未运行时明确标注“以下为预期输出，尚未在当前环境执行”。
- 不伪造工具告警、性能数据、图片、引用、执行结果或环境支持情况。
- 涉及 review 意见示例时，示范“对事不对人”的措辞，并标注严重级别（Must fix／Should fix／Nit）。

### 4. 制作并嵌入真实图片

每天至少生成 **3 个真实可打开的视觉文件**，其中至少 **2 张是技术信息图**。推荐组合：

1. 全局流程图：当天主题在检视流程（读 diff → 分维度检查 → 写意见 → 跟进修复）或 120 天路线图中的位置；
2. 核心机制图：对象生命周期时间线、所有权／引用关系、锁的持有范围、内存布局或 sanitizer 检测原理；
3. 实例对照图：缺陷代码与修复后对照、错误输出与正确输出对照、糟糕评论与专业 review 意见对照。

执行规则：

- 优先制作准确、可编辑的 SVG；需要时导出 PNG。也可将 Mermaid 渲染成 SVG／PNG后嵌入。
- SVG 统一采用手绘 sketch 风（Excalidraw-like）：
  - 线条手绘感自然，可略有不均匀和抖动，避免过于完美的直线或圆润矢量边。
  - 笔触类似马克笔或铅笔，描边略粗，线宽可有轻微变化。
  - 配色极简，一般不超过 3～4 种柔和的蓝、橙、绿、红等强调色，背景使用白色或米白色。
  - 使用矩形、网格、箭头、圆角框等简单几何形状，不画复杂 3D 或写实元素。
  - 标签使用手写感字体；英文可选 Bradley Hand、Comic Sans MS 等，中文可选楷体（Kaiti SC）等，优先保证可读性。
  - 整体类似轻松的白板涂鸦，允许标注略有错位，但技术关系必须准确、文字必须清楚。
- 图像生成工具可用时，可生成封面或类比插图，但装饰图不能计入 2 张技术信息图。
- 图像工具不可用时，直接生成简洁 SVG，不得因此退化为无图教程。
- 在正文中用相对路径嵌入图片，提供有意义的替代文本和图注，例如 `![shared_ptr 循环引用与 weak_ptr 打环](images/02-cycle-weakptr.svg)`。
- 图片必须与相邻文字共同解释问题，图中文字清楚，不把整段教程塞进图片。
- 不输出“此处插图”“图片待补充”“建议画一张图”等占位内容。
- 不把 Mermaid 源码、外部图片链接或 ASCII 图当作已完成的图片文件。
- 生成后检查文件存在且可解析；SVG 使用有效 XML，PNG／JPG 等不能是空文件。

### 5. 验证代码与教程

- 编译并运行能执行的缺陷示例（含警告与 sanitizer 配置），记录命令、编译器版本和真实输出。
- 检查所有相对图片链接、文件路径、命令和代码围栏。
- 仓库提供 [references/quality-checklist.md](../../references/quality-checklist.md) 时，逐项自检。
- 仓库提供检查脚本时，使用脚本检查结构、图片和常见占位内容：

```bash
python3 scripts/tutorial_tools.py check tutorials/day-045/README.md
```

脚本用于检查最低交付要求，不能替代技术正确性审查。

### 6. 保存与交付

未指定目录时，使用：

```text
tutorials/
└── day-045/
    ├── README.md
    ├── examples/          # 当天的示例代码（.cpp、.clang-tidy、命令脚本等）
    └── images/
        ├── 01-overview.svg
        ├── 02-mechanism.svg
        └── 03-example.svg
```

- 批量生成时，每天独立保存、独立校验，不为凑数量复用无关图片或省略实践。
- 最终回复只概述当天教程内容、实际验证情况和文件入口，不复述整篇教程。
- 用户要求推送仓库时，再执行 Git 提交；不要因生成教程自动公开或发布内容。

## 质量底线

出现以下任一情况时继续修改，不要交付：

- 只有知识点罗列，没有解释、缺陷案例和检视操作过程；
- 图片只是占位符、链接失效或只有装饰作用；
- 类比比技术原理更长，或类比导致明显错误理解；
- 缺陷示例缺少编译运行命令，用户无法复现告警或行为；
- 把预期输出写成已执行结果；
- 当天教程需要理解未解释的后置概念；
- 没有常见错误、找 bug 演练和可勾选的验收清单；
- review 意见示例含人身攻击式措辞，或未标注严重级别。
